# Rider attribute history — Implementation Plan

**Spec:** `specs/rider-attribute-history.md` · **Issue:** #95 · **Status:** proposed
**Apps touched:** `riders/`, `world/`, `teams/`

## Context you need

`riders.Rider` holds five engine attributes (`climb`, `sprint`, `flat`,
`resistance`, `positioning`) stored 1-100. The player never sees those numbers:
`riders/display.py`'s `to_display_scale(value)` floors them onto 0-10 and is the
only place that mapping happens. Two riders at 71 and 74 both show 7. See
`riders/README.md`, *Display scale: stored 1-100, shown 0-10*.

Those attributes move every week. `riders/services.py`'s `apply_weekly_growth(weeks,
extra_deltas=None)` walks every rider, folds the age curve (#58) and weekly
training (#36) through one `growth_debt` ledger, and `bulk_update`s the table.
**It already returns exactly the change information this feature needs** — one
record per rider *per attribute* whose displayed value moved, shaped
`{"rider_id", "rider_name", "team_id", "attribute", "from", "to"}`. `staff.
TrainingWeekReport` already consumes that return for the Training screen.

The caller is `world/services.py`'s `_apply_training_week(week)`, invoked once
per crossed week from `tick()`. `riders/` knows nothing about weeks or the
clock — `AGENTS.md` forbids `riders/` from importing `schedule/` or `world/`,
and that is why `apply_weekly_growth` returns records rather than writing them.

Riders are created in exactly three places, all of which call
`riders.generation.generate_roster(size, team=...)` and then `Rider.objects.
bulk_create(...)`:

- `teams/services.py:67` — `claim_team`
- `teams/management/commands/seed_teams.py:161`
- `riders/management/commands/reset_riders.py:57`

**`generate_rider` returns an *unsaved* Rider** so callers can bulk-create. That
is the single most important fact for this plan — see Design decision 3.

There are no Django signals anywhere in this codebase. Do not introduce the
first one here.

## Goal

When this is done:

1. Every rider has a history row recording their five displayed (0-10)
   attributes at the moment they were created.
2. A further row is written for a rider only in a week where at least one of
   those five displayed values changed.
3. A rider's rows are readable in chronological order, each tagged with the
   week it describes.
4. Every rider in the world is covered — managed, unmanaged and free agents.
5. Nothing is visible to the player and no API ships any of it.

## Design decisions (settled — implement these, do not substitute)

**1. One row per rider per recorded moment, holding all five attributes — not
one row per attribute change.**
`apply_weekly_growth` returns per-attribute records, so the obvious move is to
mirror that shape. Do not. #96 plots five lines on one graph and needs all five
values at every x-point; per-attribute rows would make it reconstruct each
line's value at every other line's timestamp. When any attribute moves, record
all five.

**2. Store the displayed 0-10 value, not the stored 1-100 value.**
Spec, *Rules and edge cases*. The display scale exists so a rider can improve
without the shown number moving; recording the finer value would put movement
into the database that the design deliberately hides from the player, and would
be a standing leak risk of exactly the kind `riders/README.md` calls a defect.
**Do not add a "store fine, coarsen at read time" field** — that was considered
and rejected in the spec's `Decisions taken`.

**3. The baseline snapshot is written by a service function the creation sites
call after `bulk_create` — not inside `generate_rider`, and not by a signal.**
`generate_rider` returns an unsaved instance with no primary key, so it cannot
write a related row. A `post_save` signal would work but this codebase has none
and adding the first one to a hot bulk path is a poor place to start; it would
also fire on every future `Rider.save()`, which is not what is wanted. Add
`record_initial_snapshots(riders)` to `riders/services.py` and call it at each of
the three sites, immediately after the `bulk_create`. **Load-bearing:**
`bulk_create` on PostgreSQL populates primary keys on the returned list, so pass
the list `bulk_create` returns, not the list handed to it.

**4. The weekly snapshot is written in `world/`, from the records
`apply_weekly_growth` already returns — `riders/` gains no knowledge of weeks.**
`_apply_training_week` already has both the `week` and the `changes` list. Pass
the changed rider ids to a new `riders.services.record_week_snapshots(rider_ids,
week_id)`. The `week_id` crosses as a plain integer so `riders/` still imports
nothing from `schedule/`; the model's FK is declared as the string
`"schedule.Week"`, the same import-free pattern `staff.TrainingWeekReport.week`
and `racing.Race.week` already use (`AGENTS.md`).

**5. `week` is nullable, and null means "the baseline, at creation".**
A rider generated by `claim_team` mid-season is created outside any week
transition, and `seed_teams` runs before a season exists at all. Rather than
inventing a week for them, the baseline row carries `week = NULL`. Ordering is
by `created_at`, which every row has (`core.TimeStampedModel`).

**6. Deduplicate on `(rider, week)` with a database constraint, not a
check-then-insert.**
`tick()` is the only weekly writer and `WeekTransition` already makes a week
process exactly once, so a duplicate should be impossible. The constraint is a
second line of defence, the same posture `staff.TrainingWeekReport`'s
`one_training_report_per_team_per_week` takes. Because `week` is nullable and
Postgres treats NULLs as distinct in a unique index, this constraint does **not**
restrict baseline rows — which is correct: a rider gets exactly one baseline
because exactly one code path creates them.

**7. A late tick attributes each week's change to that week.**
Already true for free: `tick()` loops `for transition in weeks:` and calls
`_apply_training_week(week)` once per crossed week, never collapsing them.
Hooking in there inherits the correct behaviour. **Do not** move the snapshot
call up to `tick()`'s body outside that loop.

**8. Existing riders get a baseline via a data migration.**
The world already has riders. Without a backfill their graphs start at whatever
week they next happen to move, which is the exact failure the ticket exists to
prevent. One data migration, `week = NULL`, current values.

**9. No API serializer, no admin registration beyond read-only, no frontend.**
Spec, *Out of scope*. #96 is the consumer.

## Data model

New model in `riders/models.py`:

```python
class RiderAttributeSnapshot(TimeStampedModel):
    rider = models.ForeignKey(
        "riders.Rider", on_delete=models.CASCADE, related_name="attribute_snapshots",
    )
    week = models.ForeignKey(
        "schedule.Week", on_delete=models.SET_NULL,
        null=True, blank=True, related_name="rider_attribute_snapshots",
    )
    climb = models.PositiveSmallIntegerField()
    sprint = models.PositiveSmallIntegerField()
    flat = models.PositiveSmallIntegerField()
    resistance = models.PositiveSmallIntegerField()
    positioning = models.PositiveSmallIntegerField()
```

| Field | Type | Null/blank | Default | Notes |
|---|---|---|---|---|
| `rider` | FK `riders.Rider` | no | — | `CASCADE`, `related_name="attribute_snapshots"` |
| `week` | FK `schedule.Week` (string ref) | **null=True, blank=True** | — | `SET_NULL`. Null = baseline at creation (D5) |
| `climb` … `positioning` | `PositiveSmallIntegerField` | no | — | **0-10 display scale** (D2). No validators beyond the field's own — a display value is derived, never user-entered |
| `created_at` / `updated_at` | from `TimeStampedModel` | — | auto | `created_at` is the ordering key |

`Meta`:

```python
class Meta:
    ordering = ["created_at"]
    constraints = [
        models.UniqueConstraint(
            fields=["rider", "week"], name="one_snapshot_per_rider_per_week",
        ),
    ]
    indexes = [models.Index(fields=["rider", "created_at"])]
```

**`week` uses `SET_NULL`, not `CASCADE`.** A snapshot must outlive schedule
churn; deleting a week must not silently delete attribute history. The row
degrades to an undated point rather than vanishing.

**`rider` uses `CASCADE`.** The spec says history is permanent, but making rider
rows themselves permanent is #42's decision (spec, *Conflicts*) and
`reset_riders` still deletes riders today. `CASCADE` matches the current world;
when #42 stops deleting riders, nothing here needs changing.

Migrations, in `riders/migrations/`:

- `0009_riderattributesnapshot.py` — the model, constraint and index.
- `0010_backfill_rider_attribute_snapshots.py` — data migration, D8.

## `riders/models.py`

Add `RiderAttributeSnapshot` as above. Nothing on `Rider` changes.

## `riders/services.py`

Two new functions. Both take already-saved riders and write rows; neither knows
what a week is beyond an opaque id.

```python
def _display_values(rider: Rider) -> dict[str, int]:
    """This rider's five attributes on the 0-10 scale the player sees."""
    return {name: to_display_scale(getattr(rider, name)) for name in ENGINE_ATTRIBUTES}


def record_initial_snapshots(riders: list[Rider]) -> int:
    """Baseline row for each newly created rider (week=None).

    Call immediately after Rider.objects.bulk_create, with the list
    bulk_create returned — its instances carry the primary keys.
    """


def record_week_snapshots(rider_ids: list[int], *, week_id: int) -> int:
    """One row per rider whose displayed value moved this week.

    `week_id` is a plain int, not a Week: riders/ may not import schedule/
    (AGENTS.md). Returns rows written.
    """
```

`record_week_snapshots` builds instances for `Rider.objects.filter(pk__in=
rider_ids)` and writes them with

```python
RiderAttributeSnapshot.objects.bulk_create(rows, ignore_conflicts=True)
```

**`ignore_conflicts=True` is load-bearing.** It is what makes the unique
constraint a silent guard rather than a crash if a week is ever somehow
processed twice — the same tolerate-the-duplicate posture
`_write_training_reports` takes with its caught `IntegrityError`, without
needing a per-row transaction, because `bulk_create` is one statement.

Note that `bulk_create(..., ignore_conflicts=True)` does not populate primary
keys on the returned instances. Nothing here needs them; return `len(rows)`
computed before the call, or re-count if an exact written figure matters — say
which in the docstring rather than leaving it ambiguous.

## `world/services.py`

In `_apply_training_week`, after the existing `apply_weekly_growth` call:

```python
changes = apply_weekly_growth(weeks=1, extra_deltas=extra)
_write_training_reports(week, changes, focus_by_team)
record_week_snapshots(
    sorted({c["rider_id"] for c in changes}), week_id=week.pk,
)
```

The set collapses the per-attribute records into one entry per rider (D1);
`sorted` only makes the write order deterministic for tests.

Import `record_week_snapshots` alongside the existing `apply_weekly_growth` /
`apply_weekly_recovery` imports at the top of the file — `world/` may import
anything (`AGENTS.md`).

**Do not add a counter to `TickRun`.** The spec ships no player-visible or
operator-visible surface, and `riders_trained` already counts the same weeks'
movement.

## `teams/services.py`, `teams/management/commands/seed_teams.py`, `riders/management/commands/reset_riders.py`

Each has a `Rider.objects.bulk_create(generate_roster(...))`. Capture the return
and pass it on:

```python
created = Rider.objects.bulk_create(generate_roster(roster_size, team=team))
record_initial_snapshots(created)
```

`teams/` importing `riders.services` is allowed — `teams -> riders` is in the
dependency graph — and `riders/` already imports `teams` only via string FK, so
no cycle. In `teams/services.py` the import goes at module scope beside the
existing `from riders.generation import generate_roster`; the lazy-import rule
in `AGENTS.md` applies to `teams -> economy`, not to this edge.

## Work items

### W1 — `riders/models.py`, `riders/migrations/0009_*`: the model ✅
Add `RiderAttributeSnapshot` with its fields, `Meta.ordering`, the
`one_snapshot_per_rider_per_week` constraint and the `(rider, created_at)`
index. Generate the migration.
**Test:** `riders/tests/test_models.py` — a case that creates two snapshots for
one rider in two different weeks and asserts both save; a case asserting a
second snapshot for the same `(rider, week)` raises `IntegrityError`; a case
asserting two baseline rows (`week=None`) for the same rider both save, proving
the constraint does not catch NULLs (D6).

### W2 — `riders/services.py`: `record_initial_snapshots` and `record_week_snapshots` ✅
Both functions plus `_display_values`. No callers yet.
**Test:** `riders/tests/test_services.py` — `record_initial_snapshots` writes one
row per rider with `week=None` and values equal to `to_display_scale` of each
stored attribute (assert on a rider at 71 showing 7, so the test would fail if
stored values were recorded — this is the check that proves D2);
`record_week_snapshots` writes one row per id with the given `week_id`; calling
it twice for the same week writes nothing the second time and does not raise.

### W3 — the three creation sites: baseline on creation
`teams/services.py`, `teams/management/commands/seed_teams.py`,
`riders/management/commands/reset_riders.py`.
**Load-bearing:** use the list `bulk_create` returns, not the list passed in
(D3).
**Test:** `teams/tests/` — after `claim_team`, every rider on the team has
exactly one snapshot with `week=None`. `riders/tests/test_reset_riders.py` —
after the command, every generated rider has exactly one baseline snapshot and
no orphan snapshots survive from the deleted population.

### W4 — `world/services.py`: the weekly snapshot
Wire `record_week_snapshots` into `_apply_training_week`.
**Test:** `world/tests/` — tick a week in which a rider's displayed value
changes and assert one snapshot row for that rider tagged with that week; assert
a rider whose displayed value did *not* change gets no row for that week; tick
two missed weeks at once and assert each week gets its own row for a rider that
moved in both (D7 — this is the test that proves late ticks attribute
correctly).

### W5 — `riders/migrations/0010_*`: backfill existing riders
Data migration giving every existing rider a `week=NULL` baseline at their
current values. Guard against re-running by skipping riders that already have a
snapshot. Reverse operation: delete baseline rows (`week__isnull=True`).
**Test:** `riders/tests/test_models.py` or a dedicated migration test — assert
the migration is idempotent by running the forward function twice against a
rider and getting one row. (If the repo has no migration-test harness, test the
extracted helper function directly rather than inventing one.)

### W6 — documentation
`riders/README.md` and `world/README.md`. See below.

## Execution order

W1 → W2 → W3 → W4 → W5 → W6.

W1 and W2 land the model and the writers with no callers, so each is green on
its own and reviewable without reasoning about the tick. W3 before W4 because
the baseline is the simpler of the two call sites and proves
`record_initial_snapshots` against real data before the weekly path depends on
the same model. W5 comes after both writers work, so the backfill is written
against a model whose shape is settled. W6 last, describing what was actually
built.

Commit after each work item. The suite must be green at every one.

## Verification

```bash
.venv/bin/python -m pytest
```

End to end, in this worktree, with `GAME_CLOCK_CLASS=world.clocks.MockClock`:

```bash
.venv/bin/python manage.py seed_user
.venv/bin/python manage.py seed_teams --claim-for test@mail.com
.venv/bin/python manage.py seed_trainers
.venv/bin/python manage.py load_season seasons/season-1.example.json
.venv/bin/python manage.py mock_clock set <season start>
.venv/bin/python manage.py tick
```

Then in `manage.py shell`, confirm:

1. Every rider has exactly one `week__isnull=True` snapshot (the baseline).
2. After several `mock_clock` advances and `tick`s, some riders have additional
   rows, each tagged with a distinct week.
3. Every recorded value is in `0..10`.

**The likeliest failure mode is silence.** If `record_week_snapshots` is wired
in but `changes` is empty every week — because growth rarely crosses a display
threshold — the feature looks implemented and records nothing. Advancing the
clock a single week is not enough evidence. **Advance a full twelve-week season
and assert at least one rider gained a non-baseline row**; a young rider well
below potential should cross a display threshold within a season
(`riders/README.md` puts a season's growth at one to two display points).

The second-likeliest is recording the wrong resolution. The W2 test that pins a
rider at stored 71 to a recorded 7 is what catches it; a test that creates a
rider at exactly 70 would pass under both behaviours and prove nothing.

## Risks

| Risk | Mitigation |
|---|---|
| Baseline written from the pre-`bulk_create` list, so every row has `rider_id=None` and the write fails or misattributes | D3 and W3 both flag it; the W3 test asserts a snapshot exists *per rider on the team*, which fails outright if ids are missing |
| Snapshots recorded at stored 1-100 resolution, leaking hidden progress | W2's test pins a rider at 71 → 7. Do not weaken it to a round-number case |
| Per-attribute rows instead of per-rider rows, because that is the shape `apply_weekly_growth` returns | D1; the set-collapse in `_apply_training_week` is the whole fix and is written out in full above |
| A late tick bunching several weeks into one row | D7; the W4 two-missed-weeks test is the proof |
| Table growth | Not a real risk — a 200-team, ~2,400-rider world writes at most ~29k rows a season even recording unconditionally, and on-change recording is far less. Recorded here only so nobody re-opens it |
| Someone adds the snapshot to `RiderSerializer` "for the frontend" | The README section states nothing serializes this; #96 owns the read path |
